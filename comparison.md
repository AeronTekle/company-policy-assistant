I compared rules-based search, an LLM using the full policy database, and an LLM using a vector index (RAG) on the same ten questions on 1 November 2026. The database contained 98 policies. The questions covered direct facts, a paraphrase, two policies in one question and missing information. Table 1 shows the results of a Codex-assisted review against the policies. Correctly identifying unavailable information counted as correct, while irrelevant extra policies or incomplete responses reduced accuracy. These results describe 30 recorded answers from a small, selected sample; they do not establish a general accuracy or hallucination rate. Table 2 reports fresh response times and API-derived token counts. LLM counts came from generation usage metadata; embedding input counts came from Gemini's countTokens endpoint using the same model and text. No character-based token estimates are used in this comparison.

For this database, I would choose full context because it avoids vector-index preparation and gave strong answers with a simpler setup. RAG used 91.1% fewer LLM tokens per answer, but also required query embeddings and an initial index. All 98 policy embeddings were rebuilt for this evaluation: preparation took 63.18 seconds, and their exact combined input count was 4,425 tokens. This setup is separate from the per-question figures. RAG response times include the extra token-count request, which averaged 0.191 seconds per query, as well as retrieval and generation. Each question was run once per method in one session, always in the order rules, full context, RAG; the timings therefore should not be treated as a controlled benchmark. Token counts from different models do not establish total monetary cost, and countTokens is an input measurement rather than a billing record. The Slack bot demonstration uses full context and identifies the relevant policy.
